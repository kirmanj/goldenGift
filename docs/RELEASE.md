# Golden Gift — Release guide

How Golden Gift is built, signed and shipped (SRS §10 Phase 10): versioning, the GitHub Actions release workflows and every secret they use, the one-time owner setup, the pre-release checklist, store steps, web and backend deploys, rollback, and the beta exit criterion.

Related: store texts and privacy answers in [store/listing.md](store/listing.md), legal drafts in [legal/](legal/) (published as `/privacy` and `/terms`).

## 1. What ships where

| Piece | Built by | Goes to |
|---|---|---|
| Android app (`com.goldengift.golden_gift`) | `.github/workflows/release-android.yml` | AAB artifact → Google Play **internal testing** |
| iOS app (`com.goldengift.goldenGift`) | `.github/workflows/release-ios.yml` | IPA artifact → **TestFlight** |
| Customer web app + `/privacy`, `/terms`, `/.well-known/*` | `.github/workflows/deploy-web.yml` | Firebase Hosting site `goldengift-iq` (`https://goldengift-iq.web.app`, later `https://goldengift.app`) |
| Admin dashboard | `.github/workflows/deploy-web.yml` | Firebase Hosting site `goldengift-admin` |
| Cloud Functions, Firestore indexes, (optionally) production rules | `.github/workflows/deploy-functions.yml` | Firebase project `goldengift-iq` (region `europe-west1`) |
| Checks on every push / PR | `.github/workflows/ci.yml` | — |

Triggers: pushing a tag `vX.Y.Z` runs the Android, iOS and web workflows; every workflow can also be started by hand (Actions ▸ workflow ▸ Run workflow). Functions are deployed **only by hand**. Each workflow builds even when its secrets are missing (proves the build) and skips the signing / upload / deploy step with a notice.

## 2. Versioning

- `mobile/pubspec.yaml` → `version: MAJOR.MINOR.PATCH+BUILD`. The **version name** (`1.0.0`) is what users see (`CFBundleShortVersionString` / `versionName`); bump it for every store release (patch for fixes, minor for features).
- The **build number** (`CFBundleVersion` / `versionCode`) must grow with every upload. CI sets it with `--build-number` = `BUILD_NUMBER_OFFSET` (repository variable, default 0) + the workflow's run number, or the `build_number` input of a manual run. The `+BUILD` part of pubspec is only used for local builds.
- If you ever upload a build by hand with a higher number, raise `BUILD_NUMBER_OFFSET` so CI stays above it (Android `versionCode` max is 2,100,000,000).
- Release = bump `version:` in pubspec → commit → tag `v1.0.0` → push the tag. The workflows stop if the tag doesn't match the pubspec version (`v1.0.0-rc1` is allowed for `1.0.0`).
- Keep `app_settings/general.minAppVersion` (dashboard ▸ Settings) at the oldest version that still works with the backend; raising it forces the update dialog (SRS §8 Versioning).

## 3. Secrets and variables (GitHub ▸ Settings ▸ Secrets and variables ▸ Actions)

Nothing secret is ever committed. Base64 values: `base64 -i <file> | pbcopy` (macOS), paste as the secret value.

### Secrets

| Secret | Used by | What it is / how to get it |
|---|---|---|
| `FIREBASE_OPTIONS_DART_B64` | android, ios, web | base64 of `mobile/lib/firebase_options.dart` (generated by `flutterfire configure`, git-ignored) |
| `ADMIN_FIREBASE_OPTIONS_DART_B64` | web | base64 of `adminDashboard/lib/firebase_options.dart`; optional — falls back to the mobile file (same web app) |
| `GOOGLE_SERVICES_JSON_B64` | android | base64 of `mobile/android/app/google-services.json` — re-download it after adding the SHA fingerprints (§4.2) |
| `GOOGLE_SERVICE_INFO_PLIST_B64` | ios | base64 of `mobile/ios/Runner/GoogleService-Info.plist` |
| `ANDROID_KEYSTORE_B64` | android | base64 of the **upload** keystore (`.jks`) — §4.2 |
| `ANDROID_KEYSTORE_PASSWORD` | android | keystore password |
| `ANDROID_KEY_ALIAS` | android | key alias (e.g. `upload`) |
| `ANDROID_KEY_PASSWORD` | android | key password |
| `PLAY_SERVICE_ACCOUNT_JSON` | android | JSON key (plain text, not base64) of a Google Cloud service account invited in Play Console with release rights — §4.2. Optional: without it the AAB is only an artifact |
| `IOS_DIST_CERT_P12_B64` | ios | base64 of the **Apple Distribution** certificate + private key exported as `.p12` — §4.3 |
| `IOS_DIST_CERT_PASSWORD` | ios | password of that `.p12` |
| `IOS_PROVISIONING_PROFILE_B64` | ios | base64 of the **App Store** provisioning profile for `com.goldengift.goldenGift` |
| `APPSTORE_ISSUER_ID` | ios | App Store Connect ▸ Users and Access ▸ Integrations ▸ App Store Connect API — Issuer ID |
| `APPSTORE_API_KEY_ID` | ios | Key ID of an API key with the **App Manager** role |
| `APPSTORE_API_PRIVATE_KEY` | ios | contents of `AuthKey_<KEYID>.p8` (shown once when the key is created). Optional: without the three ASC values the IPA is only an artifact |
| `ANDROID_MAPS_API_KEY` | android | Google Maps SDK for Android key (restricted to the package + SHA-1s) — only used when `MAPS_ENABLED=true` |
| `IOS_MAPS_API_KEY` | ios | Google Maps SDK for iOS key (restricted to the bundle id) — written to the `MAPS_API_KEY` build setting in the runner only |
| `RECAPTCHA_SITE_KEY` | web | reCAPTCHA Enterprise site key for App Check on the web (public value, may also be a variable) |
| `DART_DEFINES_JSON` | android, ios | optional extra `--dart-define`s as a JSON object (never `USE_EMULATOR`) |
| `FIREBASE_SERVICE_ACCOUNT` | web, functions | JSON key of the CI deploy service account — §4.1 |

### Variables

| Variable | Default | Meaning |
|---|---|---|
| `BUILD_NUMBER_OFFSET` | 0 | added to the run number for store build numbers |
| `MAPS_ENABLED` | unset | `true` turns the address map pin on in the mobile builds (needs the platform key secrets) |
| `RECAPTCHA_SITE_KEY` | unset | as the secret of the same name (either works) |
| `XCODE_VERSION` | runner default | e.g. `26.6` to pin `/Applications/Xcode_26.6.app` on the `macos-26` runner |

### Backend secrets (Secret Manager, not GitHub)

Set once with the Firebase CLI on the Blaze plan; `deploy-functions` fails if one is missing:

```bash
firebase functions:secrets:set OTPIQ_API_KEY     --project goldengift-iq   # phone codes (OTPIQ)
firebase functions:secrets:set ALGOLIA_ADMIN_KEY --project goldengift-iq   # search index sync
firebase functions:secrets:set ZAINCASH_SECRET   --project goldengift-iq   # ZainCash merchant secret (any placeholder while on the sandbox)
```

Non-secret function parameters live in the committed `mobile/functions/.env`: `ENFORCE_APP_CHECK`, `ALGOLIA_APP_ID`, `ALGOLIA_INDEX_NAME`, `GEMINI_MODEL`, `ZAINCASH_ENV`, `ZAINCASH_MERCHANT_ID`, `ZAINCASH_MSISDN`, `ZAINCASH_RETURN_URL`. AI Gift Search uses Gemini on **Vertex AI** with the functions' service account — enable the Vertex AI API (`aiplatform.googleapis.com`) on goldengift-iq; no key needed.

## 4. One-time setup (owner)

### 4.1 Firebase / Google Cloud

1. `goldengift-iq` on the **Blaze** plan with a billing budget alert.
2. CI deploy service account (Google Cloud console ▸ IAM ▸ Service accounts ▸ create `github-deploy`), roles: **Firebase Admin**, **Cloud Functions Admin**, **Cloud Run Admin**, **Eventarc Admin**, **Cloud Scheduler Admin**, **Artifact Registry Administrator**, **Secret Manager Admin** (the CLI grants the functions' runtime account access to each secret during deploy), **Service Account User**, **Cloud Datastore Index Admin**. Create a JSON key → secret `FIREBASE_SERVICE_ACCOUNT`; delete the downloaded file afterwards. If a deploy still reports a missing permission, add the role it names (the exact set for 2nd-gen functions changes from time to time).
3. Storage: create the default bucket (console ▸ Storage), then allow browser reads of images: `gsutil cors set mobile/storage.cors.json gs://<bucket>` (bucket name in `firebase_options.dart`, e.g. `goldengift-iq.firebasestorage.app`).
4. Authentication providers: Phone sign-in is done by our functions (no Firebase Phone Auth); enable **Google**, **Apple** and **Email/Password** (admins: `npm run auth:enable-email` in `mobile/functions`). Settings ▸ Authorized domains: add `goldengift.app` (and `admin` domain if you add one).
5. APNs: Apple Developer ▸ Keys ▸ create an **APNs** key (.p8) → Firebase console ▸ Project settings ▸ Cloud Messaging ▸ Apple app ▸ upload it with the Key ID and Team ID.
6. Recommended: Firestore point-in-time recovery or a scheduled export (`gcloud firestore export`) before launch.

### 4.2 Android / Google Play

1. **Upload keystore** (once, keep it and both passwords in the owner's password manager — losing it means a key reset through Play support):
   `keytool -genkeypair -v -keystore goldengift-upload.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload`
   Locally: copy `mobile/android/key.properties.example` → `mobile/android/key.properties` (git-ignored). CI: the four `ANDROID_*` secrets. Without either, release builds use the **debug** key (fine for `flutter run --release`, rejected by Play).
2. Play Console: create the app (default language English (US), app, free), complete *App content* (privacy policy URL, app access — §10, ads: none, content rating, target audience 18+, data safety — from [store/listing.md](store/listing.md), government app: no, financial features: none), store listing (texts + graphics).
3. **Play App Signing** (default for new apps): Google holds the app signing key; you upload with the upload key. The first AAB must be uploaded **by hand** (Testing ▸ Internal testing ▸ Create release) — take it from the `release-android` artifact. Until the app is first published, API uploads must use `play_status: draft` (workflow input).
4. Play API access: Google Cloud ▸ create a service account `play-publisher` + JSON key (no Cloud roles needed) → Play Console ▸ Users and permissions ▸ invite its email with *Release apps to testing tracks* (+ *Release to production* if you want) for Golden Gift → secret `PLAY_SERVICE_ACCOUNT_JSON`.
5. Fingerprints: Play Console ▸ Test and release ▸ App integrity ▸ App signing — copy the **app signing key** SHA-1 and SHA-256 (and the upload key's):
   - Firebase console ▸ Project settings ▸ Android app ▸ *Add fingerprint* (both keys, SHA-1 + SHA-256) — required for Google sign-in and App Check (Play Integrity). Re-download `google-services.json` → update `GOOGLE_SERVICES_JSON_B64`.
   - `mobile/web/.well-known/assetlinks.json`: replace `REPLACE_WITH_RELEASE_SHA256` with the **app signing key** SHA-256 (format `AB:CD:…`; add the upload key's too if you test sideloaded release builds). Deploy the web site. Check: `https://goldengift.app/.well-known/assetlinks.json` and Play Console ▸ Deep links.
   - Maps key restriction (if used): package `com.goldengift.golden_gift` + both SHA-1s.
6. Play Integrity: Play Console ▸ App integrity ▸ link the Google Cloud project `goldengift-iq` (needed by App Check).
7. Internal testing: add testers (email list), share the opt-in link.

### 4.3 Apple / App Store

1. Apple Developer Program on the owner's team. The Xcode project currently has `DEVELOPMENT_TEAM = 29WR8B5C48` — confirm it is the owner's team (else change it in Xcode).
2. Certificates, IDs & Profiles ▸ Identifiers ▸ `com.goldengift.goldenGift` with capabilities **Push Notifications**, **Sign in with Apple**, **Associated Domains**, **App Attest**.
3. In Xcode (`mobile/ios/Runner.xcworkspace` ▸ Runner ▸ Signing & Capabilities, signed in with the owner's team) add the same capabilities — this creates `Runner.entitlements`. **Not committed yet on purpose**: an entitlement the signing team doesn't have breaks every build, so only add them together with the team:
   - **Push Notifications** (+ Background Modes ▸ Remote notifications) — FCM pushes on iOS need it;
   - **Sign in with Apple**;
   - **Associated Domains** with `applinks:goldengift.app` — universal links for `/p/…`, `/r/…`, `/s/…`;
   - **App Attest** (environment `production`) — App Check's App Attest provider (without it the app falls back to DeviceCheck).
4. **Distribution certificate**: Xcode ▸ Settings ▸ Accounts ▸ Manage Certificates ▸ + Apple Distribution → Keychain Access ▸ export it with its private key as `.p12` (set a password) → `IOS_DIST_CERT_P12_B64` + `IOS_DIST_CERT_PASSWORD`.
5. **App Store provisioning profile** for `com.goldengift.goldenGift` with that certificate — create it **after** step 2 so it carries the capabilities → download → `IOS_PROVISIONING_PROFILE_B64`. Regenerate it (and update the secret) whenever capabilities change or the certificate is renewed (yearly).
6. App Store Connect: *My Apps ▸ +* (name Golden Gift, primary language English, bundle id, SKU `goldengift-ios`); API key (Integrations ▸ App Store Connect API ▸ Team key, role App Manager) → the three `APPSTORE_*` secrets.
7. `mobile/web/.well-known/apple-app-site-association`: replace `TEAMID` with the Team ID (two places). Deploy the web site, then check `https://goldengift.app/.well-known/apple-app-site-association` (served as `application/json`, no redirect) — Apple's CDN caches it, allow up to a day.
8. After the App Store record exists, set `app_settings/general.storeUrls.ios` (dashboard ▸ Settings) to the App Store URL so the force-update button works.
9. Recommended (engineering, not done here): add `<key>ITSAppUsesNonExemptEncryption</key><false/>` to `Info.plist` so manual uploads skip the export-compliance question (CI already answers it), and consider `$FirebaseAnalyticsWithoutAdIdSupport = true` at the top of `mobile/ios/Podfile` — the app never asks for tracking permission.

### 4.4 Domain `goldengift.app`

The app links to `https://goldengift.app/privacy`, `/terms`, product shares `/p/{id}`, referral links `/r/{code}` and Secret Santa invites `/s/{code}`. They only work once **goldengift.app is connected to the `goldengift-iq` Hosting site**: Firebase console ▸ Hosting ▸ goldengift-iq ▸ *Add custom domain* → add the TXT / A records at the registrar → wait for the certificate. Until then the pages live at `https://goldengift-iq.web.app/privacy` and `https://goldengift-iq.web.app/terms` (use those URLs in the store consoles meanwhile, and update them after the switch).

`firebase.json` (goldengift-iq site): `/privacy` → `/privacy.html` and `/terms` → `/terms.html` are rewritten **before** the SPA catch-all; static files always win over rewrites, so `/.well-known/assetlinks.json` and `/.well-known/apple-app-site-association` are served as files (the latter with `Content-Type: application/json`). Verified with the Hosting emulator; firebase-tools 15 also uploads `.well-known/` despite the `**/.*` ignore rule (it only skips dot-*files*).

### 4.5 Legal pages

Edit `docs/legal/privacy_policy.md` / `terms_of_service.md` (three languages each), then `python3 docs/tools/build_legal_pages.py` regenerates `mobile/web/privacy.html` / `terms.html` (`--check` verifies they are current). Before launch: owner / lawyer review, fill every `[bracket]`, native Arabic + Kurdish read-through, **remove the DRAFT banners** (the `> **DRAFT …**` lines), update "Last updated", rebuild, deploy the web. Account-deletion link for Google Play: `https://goldengift.app/privacy#en-s7`.

## 6. Android release

1. Bump `version:` in `mobile/pubspec.yaml`, merge to `main`, tag `vX.Y.Z`, push the tag (or run *Release · Android* by hand).
2. The workflow writes the Firebase config from secrets, decodes the upload keystore, builds `flutter build appbundle --release --build-number=<N> --dart-define-from-file=…`, checks the bundle is not debug-signed, stores it as an artifact and uploads it to the **internal** track when `PLAY_SERVICE_ACCOUNT_JSON` is set.
3. Play Console ▸ Internal testing: the release appears (status *completed*, or *draft* — then review and roll out). Testers update from the Play Store.
4. Promote the same release to closed / open testing or production from the Play Console (*Promote release*) once the beta exit criterion (§11) is met; use a staged rollout (e.g. 10 % → 50 % → 100 %) for production.

Local equivalent: `cd mobile && flutter build appbundle --release` with `android/key.properties` in place.

## 7. iOS release

1. Same tag as Android, or run *Release · iOS* by hand (runner `macos-26`, Xcode 26 — required for App Store uploads).
2. With the signing secrets the job imports the certificate into a temporary keychain, installs the profile, switches the Runner target's Release configuration to manual signing **in the runner only** (`.github/scripts/ios_manual_signing.rb`), builds `flutter build ipa --release --export-options-plist=…` and uploads the IPA to **TestFlight** when the App Store Connect API key secrets exist. Without signing secrets it builds an unsigned archive (`--no-codesign`) only.
3. App Store Connect ▸ TestFlight: the build appears after processing (Apple emails); add it to the internal testing group (and to an external group after Beta App Review).
4. Release: App Store ▸ + version → pick the build → submit for review (phased release recommended).

Local equivalent: open `mobile/ios/Runner.xcworkspace` signed in with the owner's team → `flutter build ipa --release` → upload with Xcode Organizer or Transporter.

## 8. Web deploys

> **Local web builds:** run `flutter clean && flutter pub get` before `flutter build web --release` whenever packages changed. A stale `.dart_tool/flutter_build` cache once produced a dashboard bundle without the `shared_preferences` web plugin — a blank white page in production (2026-10-22). CI builds start clean. If a startup still fails, the dashboard now shows "could not start" with the error instead of a blank page, and logs it to the browser console.

*Deploy · Web* (manual, or on a `v*` tag): builds the customer web app (`mobile/build/web`, including `privacy.html`, `terms.html`, `.well-known/*`) and the admin dashboard (`adminDashboard/build/web`) with `RECAPTCHA_SITE_KEY` when set, then `firebase deploy --only hosting:goldengift-admin,hosting:goldengift-iq` with `FIREBASE_SERVICE_ACCOUNT`. Input `target` = both / admin / customer.

Local equivalent (repo root): `cd adminDashboard && flutter build web --release` · `cd mobile && flutter build web --release` · `firebase deploy --only hosting --project goldengift-iq`.

## 9. Functions and production rules

*Deploy · Functions* (manual only): `npm ci`, build, typecheck, unit tests, emulator + security-rules suites, then `firebase deploy --only functions,firestore:indexes`. Inputs:
- `deploy_rules: true` — also deploys `firestore:rules,storage` from the **production** files: the job copies `mobile/firestore.production.rules` → `mobile/firestore.rules` and `mobile/storage.production.rules` → `mobile/storage.rules` inside the runner's checkout (the paths `firebase.json` deploys), deploys, and the runner is thrown away — nothing is committed. (Once production rules are live for good, the Phase 10 change is to make `firebase.json` point at the production files.)
- `force: true` — passes `--force` (deletes deployed functions / indexes that are no longer in the source). Leave off unless you mean it.

Local equivalent: `cd mobile/functions && npm run build && npm test`, then from the repo root `firebase deploy --only functions,firestore:indexes --project goldengift-iq`.

### 9.1 Phase 11 rollout — gift types & Reels (once)

From the repo root, in this order (indexes build for a few minutes; the app's new filters need them):

Then upload reels in the dashboard (Reels ▸ New reel: product, MP4 ≤ 100 MB, vertical 9:16, ≤ 60 s). Products saved before Phase 11 show "Gift for: not set" in the dashboard until the backfill has run.

## 10. App Review access

Reviewers can't receive OTPIQ codes on Iraqi numbers, and checkout needs a verified phone (AUTH-4). Use the **store-review demo login** built into `sendOtp` / `verifyOtp`:
1. Pick a dedicated number (E.164, e.g. a spare Iraqi number you control) and sign it up once in the app as a normal customer (name "App Review").
2. Set `REVIEW_PHONE=<that number>` in `mobile/functions/.env` and `firebase functions:secrets:set REVIEW_OTP_CODE` (6 digits), then redeploy `sendOtp` and `verifyOtp`. For that number no code is sent and only the configured code is accepted; every other number is unaffected. Leave either value empty to disable it.
3. Put the number + code in App Store Connect ▸ App Review Information and Play Console ▸ App content ▸ App access, with a saved address and a note that cash on delivery orders can be placed and are cancelled by ops. Mention that guests can browse without signing in and where account deletion is (Profile ▸ Settings).
4. After approval you may keep it (reviews of later versions need it) — rotate the code if it leaks.

## 11. Beta and the exit criterion

- Internal testing (Play) and TestFlight internal group for the team; then a closed beta of real customers in at least two launch cities, covering en / ar / ckb, light / dark, iOS / Android, cash on delivery and (if live) ZainCash, partner orders from the dashboard.
- **Exit criterion (SRS §10 Phase 10): zero P1 bugs during a 1-week beta.** P1 = crash or data loss, wrong money (prices, totals, wallet, credits, refunds, promo, referral), an order that cannot be placed / delivered / cancelled, a security or privacy leak, or a broken sign-in. Any P1 found restarts the week after its fix ships.
- Track bugs in one list with severity, platform, build number; watch Crashlytics (crash-free users ≥ 99.5 %), function error logs and App Check metrics daily.

## 12. Rollback

- **Android**: Play Console ▸ halt the staged rollout; ship a fix with a higher build number (Play can't install a lower `versionCode`). Internal testing can promote an older release.
- **iOS**: App Store Connect ▸ pause the phased release, or remove the version from sale while a fix goes through review; TestFlight builds can be expired.
- **Force update**: raise `app_settings/general.minAppVersion` to make broken versions update (only once the fixed build is live in the store); `maintenanceMode` shows the maintenance screen to everyone.
- **Web**: Firebase console ▸ Hosting ▸ site ▸ release history ▸ *Rollback* (or redeploy an older tag).
- **Functions**: redeploy an older tag through *Deploy · Functions* (run the workflow from that tag) — functions are versionless, the last deploy wins. Secrets keep their versions in Secret Manager.
- **Rules**: rerun *Deploy · Functions* from a known-good commit, or Firebase console ▸ Firestore / Storage ▸ Rules ▸ history ▸ restore. Back to dev-mode rules only in an emergency (they allow any signed-in write).
- **Data**: restore from point-in-time recovery / the scheduled export (§4.1).

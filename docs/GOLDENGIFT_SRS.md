## 1. Introduction

### 1.1 Purpose
This document specifies everything needed to implement the Golden Gift platform: screens, behaviour, data model, backend, non-functional requirements and the delivery phases. It is written so that each phase can be implemented in order without re-deciding scope.

### 1.2 Product summary
Golden Gift is a mobile marketplace for personalized and occasion gifts (flowers, frames, engraved items, printed products, handmade goods, gift cards, breakfast boxes, …) for Iraq and the Kurdistan Region. Customers browse by category or occasion, customize a product (text, photos, colors, sizes, dates), pay (cash on delivery, wallet, card/e-wallet gateways), and track orders. Partners (vendors) sell through the platform; admins manage the catalogue, orders, promotions, wallets and content from a web dashboard.

### 1.3 Scope of this release
- **Mobile customer app** (Flutter: iOS, Android, Web) — all screens in §5.
- **Admin dashboard** (Flutter Web) — §9.
- **Backend** on Firebase (Auth, Firestore, Storage, Messaging, Analytics, App Check) with a small set of Cloud Functions — §6–§7.
- **Seller (partner) features** are limited in v1 to onboarding + product/order management inside the admin dashboard with a `seller` role; a dedicated seller app is out of scope.

### 1.4 Definitions
| Term | Meaning |
|---|---|
| Customer | End user buying gifts. |
| Guest | Unauthenticated user browsing the catalogue. |
| Partner / Seller / Store | A vendor whose products are listed on Golden Gift. |
| Admin | Golden Gift staff using the dashboard. |
| Option group | A customization input on a product (Frame Color, Text 1, Upload your photos, …). |
| Credits | Promotional wallet balance earned through referrals / gift cards; spendable only inside the app. |
| Preparation days | Days a partner needs before the item can ship. |
| IQD | Iraqi Dinar, the single currency of the platform (0 decimals). |

### 2.4 Assumptions & constraints
- Phone number is the primary identity (OTP); email is collected but optional for login.
- Default country code `+964`; other codes selectable.
- All prices are stored and displayed in IQD. (Reference screens show `$`; Golden Gift shows `12,000 IQD`.)
- Delivery is limited to a list of served cities (`app_settings/cities`); each product may be restricted to a subset.
- Cloud Functions are deployed for this project (unlike BB). Every client feature that depends on a function must show a friendly error if the call fails and must never leave data half-written (use Firestore transactions / batched writes).

## 4. Functional requirements — cross-cutting

### 4.1 Authentication (FR-AUTH)
| ID | Requirement |
|---|---|
| AUTH-1 | Sign Up collects **Your Name**, **Email**, **Mobile Number** (country-code picker, default +964, flag shown) and an optional **referral code** (collapsed link "Have a referral code?" that expands an input). Screen: IMG_4475. |
| AUTH-2 | Submitting Sign Up sends a one-time code through **OTPIQ** (Iraqi gateway: WhatsApp first, SMS fallback) via the `sendOtp` function; `verifyOtp` checks it and returns a Firebase custom token the app signs in with (no Firebase Phone Auth, no reCAPTCHA). Codes: 6 digits, stored hashed (scrypt), 5-minute expiry, 5 wrong attempts, one active code per phone; rate limits 4 codes / 30 min per phone, 10 / 15 min per device IP, and a platform-wide daily ceiling; at most 15 wrong codes per phone per rolling day (then that number cannot be verified until the window rolls). A deployed function without the OTPIQ key refuses (`unavailable`) — codes are never written to the logs outside the Functions emulator. **Store review demo account:** App Store / Play reviewers cannot receive OTPIQ codes, so one number (`REVIEW_PHONE`, functions/.env, E.164) signs in with one fixed code (`REVIEW_OTP_CODE`, Secret Manager): for that number `sendOtp` sends nothing (no OTPIQ call, no emulator mirror) but applies the usual limits and stores the hashed code, and `verifyOtp` accepts only that code (constant-time) with the usual attempt counter and lockout, logging `review login` with the number masked; either value empty = off (normal flow). OTP screen: 6-digit boxes, resend after 60 s, iOS SMS autofill. |
| AUTH-3 | On first successful OTP the app writes `users/{uid}` (§6.1) with the sign-up fields and, if one was entered, `referralCodeEntered`. The app never writes `wallets`, `referrals` or the user's own `referralCode`: the Firestore trigger `onUserCreate` (§7) generates the unique 6-char `referralCode`, creates `wallets/{uid}` with 0 balance and 0 credits, and — when `referralCodeEntered` belongs to another user — sets `referredBy` and creates the `referrals` doc. The app must not assume the wallet exists immediately (stream it; show 0 until it arrives). |
| AUTH-4 | Sign In = phone + OTP (same `sendOtp` / `verifyOtp` flow — signing in with a new number simply creates the account). Google and Apple sign-in buttons are shown under "Or"; an account created socially must still verify a phone number before checkout, through the `changePhone` flow. |
| AUTH-5 | "Continue as a guest" opens Main. Guest actions that require an account open a bottom sheet "Sign in to continue" with Sign In / Sign Up. |
| AUTH-6 | Session persists until logout. Logout clears local cart cache, keeps device language. |
| AUTH-7 | Account deletion (Settings) — required by App Store: deletes auth user, anonymizes `users/{uid}` (keeps orders for accounting). |
| AUTH-8 | Validation: name 2–50 chars; email RFC-valid if provided; phone 10 digits for +964 (configurable per country code); referral code must be 6 characters. Inline errors in error-red under the field. Whether the referral code exists, is the user's own or comes from the same device is checked by `onUserCreate` (`users` docs are private, so the app cannot look codes up); an invalid code is ignored, sign-up still succeeds, and the user gets an in-app notification that the code was not applied. |

### 4.2 Localization (FR-L10N)
- All user-facing strings come from ARB files; three languages; RTL mirrored layouts for `ar`/`ckb`.
- Catalogue content (categories, products, banners, option labels, gift-card templates, promo descriptions) is **trilingual** in Firestore: `title`, `titleAr`, `titleKu` (and `description*`). Fallback order: current → en.
- Language switch in Profile ▸ Language, applied immediately without restart.

### 4.3 Locations / delivery coverage (FR-LOC)
- `app_settings/cities` lists served cities (default: Erbil, Sulaymaniyah, Duhok, Baghdad, Basra, Mosul, Kirkuk) — trilingual names, delivery fee per city, `isActive`.
- A product may define `availableCities[]`; when non-empty, Product Details shows the overlay **"Available only in: Erbil, Duhok"** (IMG_4494) and Checkout rejects addresses outside that list with a clear message per cart line.

### 4.4 Pricing, discounts and badges (FR-PRICE)
- Product has `price` and optional `compareAtPrice` (old price). When `compareAtPrice > price`, UI shows old price struck-through and an error-red pill badge with the rounded percentage (IMG_4481: `$35.0 ~~$40.0~~ 13%`).
- `isFeatured` shows the gold-shimmer **★ Featured** badge on the image's top-left corner (IMG_4477).
- Product cards show up to 5 colour dots (bottom-right of image) taken from the first `colorSwatch` option group (IMG_4481).

### 4.5 Notifications (FR-NOTIF)

- Events: order status changes, special-request reply, referral credited, gift card received, Secret Santa draw, admin broadcast.

### 4.6 Sharing & deep links (FR-SHARE)
- Product **Share** button (IMG_4494) shares `https://goldengift.app/p/{productId}` (Firebase Hosting + Dynamic-link-style routing handled in-app via `go_router` on web and app links on mobile).

### 5.6 AI Gift Search
**Status (owner, 2026-10-22): hidden for now.** Built and deployed, but switched off with `AppFeatures.aiGiftSearch` (build with `--dart-define=AI_GIFT_SEARCH=true` to bring it back): no bar in the Home header and `/ai-gift-search` opens Home.

Screen: large text area "Describe who it's for or the occasion" (e.g. "my sister's graduation, she loves plants, budget 50,000"), optional chips for occasion / budget / recipient, gold **Find gifts** button. Calls Cloud Function `aiGiftSearch({query, locale, budgetMax})` which asks Gemini to map the query to category ids + keywords, then returns up to 12 product ids ranked; the app displays them as product cards with a one-line "why" caption. Each query is logged to `ai_searches`. Rate limit 20 queries / user / day (function enforces; guests 10 / IP / day; Iraq calendar day; `resource-exhausted`). Fallback when the function fails (`unavailable` when Gemini fails or answers nothing usable) or is rate-limited: plain keyword search over `products.searchKeywords`.
How it works (Phase 9): Gemini step 1 turns the query + the active categories (trilingual names) into `{categoryIds ≤ 5, keywords ≤ 10 (English + the query language), budgetMax?, recipient?, occasion?}` (structured output); candidates come from two Firestore queries on `products` — `categoryIds array-contains-any` and `searchKeywords array-contains-any` (keywords tokenized with the shared search tokenizer), each ordered by `price` desc under the budget (the request's, else the one Gemini read) or by `salesCount` desc, ≤ 30 each — then active / in stock / within budget, de-duplicated and scored (keyword match ×2 + category match); Gemini step 2 picks ≤ 12 of the best 30 and writes the one-line reason in the customer's language (Kurdish = Sorani, Arabic script). The customer's text is passed to the model as data, never as instructions.

### 5.7a Coming soon category
Owner request (2026-10-22): when a category has no products yet or has a problem, Admin switches it to **Coming soon** instead of hiding it. A category has three states (§9 Categories): **Available** (`isActive`, not `comingSoon`) — normal; **Coming soon** (`isActive` and `comingSoon`) — still listed everywhere categories are listed, but opening it shows this page instead of products; **Hidden** (`isActive == false`) — not shown anywhere. A subcategory (`parentId`) of a Coming soon category is treated as Coming soon too (the page then shows the subcategory's name and icon, and its own note or else the parent's).
- **Every entry point** — Home category tile, All Categories, the Products list chips, Discover chips (compact inline version, §5.4 item 12), banner action `category`, the deep link `/products?category={id}` — reaches the same gate: the Products list (§5.8) shows the coming-soon page whenever its category is Coming soon (it waits for the category list before querying, so no product grid flashes and no product reads are spent). Products themselves are **not** hidden anywhere else (search, Popular / Featured / For you, Product Details, wishlists, carts, orders): a product may belong to several categories. For you skips a most-viewed category that is Coming soon.
- **Page layout (top → bottom):** app bar (back · cart); a rounded gold-gradient hero (`headerGradient`) with a soft radial glow, halo rings and twinkling sparkles, the category icon on a glossy gold-rimmed medallion (gift emblem when there is no icon) that floats gently with a slow light sweep, a dark **Coming soon** eyebrow pill, the category name as a large title and the line "Curated with care. Arriving soon."; a card with the message "We're crafting something special for {category}. Our team is working on it — in the meantime, discover beautiful gifts in our other categories.", the optional admin note (`comingSoonNote`, trilingual, ≤ 140 characters, e.g. "Arriving before Ramadan") as a gold quote line, a gold **Explore all categories** button (→ All Categories) and an outline **Back to home** button; **Explore other categories** — a horizontal row of Available categories (never Coming soon or hidden ones; tap opens that category in place) with View All; **Gifts you might love** — a horizontal row of Popular products (§5.4 item 4) with wishlist hearts and View All.
- Back: returns to the previous products list when the page was reached from a chip of that list; otherwise pops, or opens Home when the page was opened by a deep link. Animations stop when the system asks for reduced motion.
- **AC:** every entry point shows the page; no overflow at 320 px with 130 % text in en / ar / ckb, light and dark; text contrast ≥ 4.5:1 (dark text on the gold, gold text only as `goldText`); 48 dp tap targets with labels.

## 6. Data model (Firestore)

All documents carry `createdAt`, `updatedAt` (server timestamps). Trilingual fields use suffixes `Ar`, `Ku`. Enum string values are listed in §6.15 and must match `app_constants.dart` / `admin_constants.dart`.

### 6.1 `users/{uid}`
`name`, `email?`, `phone` (the account's VERIFIED number — `countryCode + phone` equals the ID token's `phone_number`; set at sign-up from the OTP-verified number, changed only by `changePhone`), `countryCode`, `photoUrl?`, `birthday?`, `gender?`, `city?`, `locale`, `role` (customer/seller/admin), `storeIds[]`, `referralCode` (set by `onUserCreate`), `referralCodeEntered?` (written by the app at sign-up), `referredBy?` (uid, set by `onUserCreate`), `profileCompleted`, `fcmTokens[]`, `notificationsEnabled`, `totalOrders`, `totalSpent`, `lastSeenAt`, `isBlocked`, `deviceId` (random per-install id written at sign-up, used for same-device referral checks), `isDeleted`, `deletedAt` (set by `deleteAccount`).
Subcollections: `addresses/{id}` (`label, name, phone, city, area, street, building, floor, notes, lat?, lng?, isDefault`), `saved_cards/{id}` (`gateway, token, brand, last4, expMonth, expYear`).

### 6.2 `stores/{storeId}`
`name*`, `description*`, `logoUrl`, `coverUrl`, `ownerUid`, `phone`, `city`, `status` (pendingApproval/active/suspended), `ratingAvg`, `ratingCount`, `productCount`, `ordersCount`, `commissionPercent` (0–50, set at approval), `createdAt`; set by the functions: `approvedAt`, `approvedBy`, `statusReason` (last suspend / reactivate reason), `statusUpdatedAt`, `statusUpdatedBy`. Created only by `submitPartnerApplication` (`status = pendingApproval`, `name`/`nameAr`/`nameKu` = the store name, empty description, zero counters and commission); approved / rejected by `reviewPartner`, suspended / reactivated by `setStoreStatus`. Live stores (active / suspended) are public; a pending application only to its owner and admins (§6.17).
Subcollection `private/{doc}` — readable only by the owner (the doc carries `ownerUid`), the store's seller and admins, written only by functions: `private/application` = what the partner sent (`storeName, ownerName, phone (E.164), city, category, instagram?, samplePhotos[] (≤ 5, Storage partner_applications/{uid}/…), ownerUid, submittedAt`); a rejection archives it there (`rejectedAt, rejectReason, rejectedBy, store{}` = the deleted store doc) and deletes `stores/{id}`, so the owner may apply again. Payout details (bank / wallet info) go in another private doc later — never on the public store doc.

### 6.4 `products/{id}`

optionGroups: [{
  id, type (OptionType), label*, required, sortOrder, maxLength?, minPhotos?, maxPhotos?,

Subcollection `reviews/{orderId}_{uid}`: `productId, userId, userName` (first name), `storeId` (the product's), `rating` (1–5), `text` (≤ 500), `images[]` (≤ 3, Storage `reviews/{uid}/{orderId}_{productId}/{n}.jpg`), `orderId, isApproved` (default `false`), `createdAt`; `moderatedBy`, `moderatedAt` when an admin approves / hides it (via a collection-group query on `reviews`). `onReviewWrite` keeps the product's and the store's `ratingAvg` (2 decimals) / `ratingCount` from approved reviews.

### 6.7 `orders/{orderId}`
`orderNumber` (GG-YYMM-#####), `userId`, `storeIds[]`, `items[]` (cart item snapshot + `storeId`, `status` per item for multi-vendor), `subtotal`, `discount`, `promoCode?`, `creditsUsed`, `walletUsed`, `deliveryFee`, `total`, `paymentMethod`, `paymentStatus`, `paymentRef?`, `address{}` (snapshot), `deliveryDate`, `deliverySlot?`, `isGift`, `giftMessage?`, `hidePrices`, `status`, `cancelReason?`, `orderType` (standard/giftCard/specialRequest; a giftCard order also has `giftCard{templateId, amount, recipientName, recipientPhone?, recipientEmail?, message, photoUrl?, scheduledAt? (ISO)}` and `giftCardId?` (set when the card is issued), a specialRequest order `specialRequestId`; both have ONE line with `productId ''`, `storeId 'golden-gift-home'`), `referralCredited` (this order paid its customer's referral `orderBonus`), `refundedToWallet` (anything was returned to the wallet) + `refundedCredits`, `refundedBalance`, `refundedAt?` (what has been returned so far — a refund only pays the difference), `promoReleased?` (its promo usage was given back on cancellation), `rewards{}`, `statusNote?`, `statusUpdatedBy?`, `statusUpdatedByRole?` (`customer` / `admin` / `seller`; set by whoever changes `status`; `onOrderStatusChange` copies them into the history entry), `clientRequestId` (idempotency key of `placeOrder`; the order id is `sha256(uid:clientRequestId)`, 20 hex characters), `productIds[]` (Phase 9: the products of its lines, set by `placeOrder` on every new order — the review rules check "the customer bought it" against it), `paymentDueBy?` (Phase 9, gateway orders: placement + 30 min; an unpaid order is cancelled after it), `paidAt?` (when a gateway confirmed the payment; `paymentRef` = the gateway transaction id). Phase 10 partial cancellation (a seller cancels its lines of a multi-vendor order that goes on, `updateOrderItems`): each such line gets `stockReleased: true` (its stock went back at once; no later cancellation releases it again, and a whole-order status change can never put it back on the flow — `onOrderStatusChange` restores `cancelledBySeller`); `lineCancellations` (count, the wallet transaction ids `orderItems-{orderId}-{n}-1|2`); for an unpaid order `subtotal` / `discount` / `total` are recomputed without the cancelled lines and `originalSubtotal` / `originalDiscount` keep the checkout figures; for a paid one they stay as charged and the refund is in `refundedCredits` / `refundedBalance`.
Subcollection `status_history/{id}`: `status, byUid, byRole, note, at`.
Payment (Phase 7): `discount` (promo), then `creditsUsed` (when the customer uses credits), then `walletUsed` (balance, only for `paymentMethod = wallet`, which must reach `total` 0 and is `paid` at creation); `total` is what is collected (cash on delivery / online).
Online payment (Phase 9, ZainCash): the order is created `paymentStatus pending` with `paymentDueBy` (stock, promo and credits reserved as usual; `total` ≥ 1,000 IQD), paid through a `payment_sessions` doc (§6.14) → `paymentStatus paid` + `paymentRef` + `paidAt`. A failed payment cancels it (`cancelledByBuyer`, `cancelReason 'payment_failed'`, `paymentStatus failed`, `statusUpdatedByRole 'system'`), so does running out of time (`'payment_expired'`), through the customer-cancellation path (stock, credits and promo usage back). Cancelling an order that was already paid online returns its `total` to the wallet balance. A payment that arrives for an order that no longer waits for it is credited to the wallet balance (`refund` transaction).

`imageUrl*`, `placement` (homeTop/homeMid1/homeMid2/homeBottom), `action{type: category|product|url|route, value}`, `sortOrder`, `isActive`, `startAt?`, `endAt?`.

### 6.9 `promo_codes/{code}`
`code` (doc id, upper-case), `title*`, `description*`, `type` (percent/fixed), `value`, `maxDiscount?`, `minOrder?`, `usageLimit?`, `usageCount`, `perUserLimit`, `firstOrderOnly`, `categoryIds[]?`, `storeIds[]?`, `isPublic`, `isActive`, `expiresAt`.
`promo_codes/{code}/usages/{uid}` → `count`, `updatedAt` (functions only; the customer reads their own).
Rules (shared by `mobile/lib/core/utils/promo_rules.dart` and `functions/src/orders/promoRules.ts`, fixture `mobile/test/fixtures/promo_cases.json`), checked in this order, the first failure being the `PromoRejection`: `notFound` · `inactive` (`!isActive` or `value ≤ 0`) · `expired` (now ≥ `expiresAt`) · `usageLimit` (`usageCount ≥ usageLimit`, all customers) · `perUserLimit` (0 = unlimited) · `firstOrderOnly` (the customer has a non-cancelled order: `users.totalOrders > 0`) · `minOrder` (whole-cart subtotal) · `notApplicable` (no line matches `categoryIds` / `storeIds`). Discount on the eligible lines only: percent = ⌊eligible × min(value, 100) / 100⌋ capped by `maxDiscount` (> 0), fixed = value; never more than the eligible subtotal. Codes are matched without spaces, upper-case. `placeOrder` counts the usage (`usageCount` + 1, `usages/{uid}.count` + 1) in the order's transaction; a cancellation gives it back.

### 6.10 `gift_card_templates/{id}` and `gift_cards/{id}`
Template: `name*`, `artworkUrl`, `gradientStart/End`, `presetAmounts[]`, `minAmount`, `maxAmount`, `sortOrder`, `isActive`.

### 6.11 `wallets/{uid}`
`balance` (real money: refunds, top-ups), `credits` (promotional: referrals, gift cards), `currency`. Subcollection `transactions/{id}`: `type` (WalletTxnType), `amount` (+/-), `bucket` (balance/credits), `title*`, `orderId?`, `referralId?`, `giftCardId?`, `byUid?` + `reason?` (admin adjustments), `balanceAfter`, `creditsAfter`, `createdAt` — one per movement, so replaying a wallet's transactions always ends at the wallet. Ids `{prefix}-{n}` in movement order (`order-{orderId}-1` credits, `-2` balance; `joinBonus-{referralId}-1`; `orderBonus-{referralId}-1`; Phase 9 `topUp-{sessionId}-1` for a wallet top-up and `payment-{sessionId}-1` for a late online payment credited back).

### 6.17 Security rules (enforced in Phase 10, summarised)
Each phase writes the rules and emulator rule tests for the collections it introduces; dev-mode rules stay deployed until Phase 10.
Public read: products, categories, banners, gift_card_templates, app_settings. `reels` (Phase 11): read when `visible == true` (queries filter on it) and by admins; written by admins only (functions keep the derived fields); Storage `reels/` public read, admin write of the poster image or a `video/mp4` video under 100 MB. Products (Phase 11): `giftFor`, when written (create, or an update that changes it), is a list of at most the three `GiftAudience` values — for admins and sellers alike; `forKeys` is rewritten by `onProductWrite` whatever a client sends. Owner-only: users/*, carts, wishlists, notifications (read), wallets (read). On their own `users` doc, customers may not write `role`, `storeIds`, `referralCode`, `referredBy`, `isBlocked`, `totalOrders`, `totalSpent`; `createdAt`/`updatedAt` must be server timestamps; an anonymized (`isDeleted`) profile is read-only. Notifications and referrals are readable only through queries filtered to the signed-in user (referrals: `referrerUid ==` own uid; admins read, list and count all). The rules live in `mobile/firestore.production.rules` / `storage.production.rules` with emulator tests in `mobile/functions/test/rules/`. Orders: created only by `placeOrder` (no client create / delete), read by owner / admin (seller of an included store from Phase 8), updated by admins only with the dashboard's status keys (`status, statusNote, statusUpdatedBy` = own uid, `statusUpdatedByRole` = `admin`, `items`, `updatedAt`, `cancelReason`); `status_history` written only by functions. Carts, wishlists and addresses: owner-only with shape checks; `users.fcmTokens`: the owner adds one token or removes tokens, ≤ 10. Wallets (+ `transactions`, `credit_lots`: owner / admin read), referrals, gift_cards, promo usage (`usages/{uid}`: owner / admin read): function write only. `promo_codes`: get by id for any signed-in user, public + active codes for everyone, list only with `isPublic == true && isActive == true` (admins: everything); admin create with `usageCount` 0, update never touching `usageCount` / `code`, delete only when unused (the dashboard writes its audit entry in the same batch). Admins read every `users` doc and its addresses. Phase 8: `gift_cards` read by the purchaser or the recipient (queries filtered on `purchaserUid` / `recipientUid` ==) and admins, admin update only to `disabled` (+ `disabledReason/By/At`, `updatedAt`); `special_requests` created by the owner with exactly the app's keys (`status submitted`, `lastMessageBy customer`, server timestamps), read by the owner (queries `userId ==`) and admins, updated by the owner only on `lastMessageAt/By/updatedAt`, by admins only on `status` (never to `accepted`), quote, assignment, reject reason and markers; `messages` created by the owner (`role customer`) or an admin (`role admin`) in their own name, never edited; `stores` public when active / suspended (a missing store reads as missing), owner / seller / admin always, created / approved / suspended only by functions, profile fields editable by admins (+ commission 0–50) and by the store's seller while active (not status / commission / owner / counters); `stores/{id}/private/**` read by owner, seller, admins, written by functions; sellers create / update products of their own store while it is active (never `storeId`, `isFeatured` or the counters; no delete), read orders whose `storeIds` contain their store (queries `storeIds array-contains`) and their `status_history`, never write orders (`updateOrderItems`), read their own `admins` doc and append `admin_audit_log` entries in their own name for `products/…` and their store. Phase 9: `products/{id}/reviews/{orderId}_{uid}` created / replaced by the author with exactly the app's keys (`isApproved false`, `createdAt` server time, `storeId` = the product's) only for their own `delivered` order whose `productIds` contain the product, updated by admins only on `isApproved` + `moderatedBy` (own uid) + `moderatedAt` (server time), never deleted by clients; every `reviews` doc (also as a collection group) readable when approved (queries filter `isApproved == true`), by its author and by admins. `secret_santa_groups` created by the organiser with exactly the app's keys (`status open`, `memberUids == [own uid]`) together with their own member doc (same batch), read by members (queries `memberUids array-contains` own uid) and admins, updated by the organiser while open on `name / budget / exchangeDate`; `members` read by members and admins, a member's own `wishlistNote`, the organiser's `exclusions` while open; `assignments/{uid}` read only by that member and admins, written only by functions. `ai_searches`: admin read only. `payment_sessions`: owner / admin read, functions write. Admin = custom claim `admin == true`; seller = claim `seller == storeId` (never together).
**Phase 10 — final production rules (deploy at launch by pointing `firebase.json` `firestore.rules` / `storage.rules` at `firestore.production.rules` / `storage.production.rules`):** admin = the `admin` claim **and** a live `admins/{uid}` doc whose `role` is super / ops / content / finance (a revoked admin is a stranger at once, not when the token expires; a `seller` admins doc never counts); a seller's writes need the claim **and** the live store (`active`, `ownerUid` = the caller) — products, the store profile, and audit entries only for their store or one of their own products; admins never write `users` docs (blocking, wallets, roles go through the functions); a profile's `phone` / `countryCode` may only be the ID token's verified `phone_number` (or absent) and every profile field is bounded (email ≤ 254, photoUrl ≤ 2048, deviceId ≤ 128, city ≤ 64, gender ≤ 20, locale en / ar / ckb, booleans / timestamps typed, countryCode `+` and ≤ 4 digits); both files end with an explicit catch-all deny (`match /{document=**}` / `match /{allPaths=**}`, `allow read, write: if false`). Storage: no public write anywhere; every write is a raster image (JPEG / PNG / WebP / GIF / HEIC, never SVG), non-empty and under 10 MB — except reel videos (`reels/`, admins, `video/mp4` under 100 MB); admin folders need the live admins doc too. Guards (`functions/test/rules/rulesCoverage.test.ts`): every top-level collection and subcollection of `FirestorePaths` has an explicit match under its parent, the rules name no unknown collection, functions-only collections deny every client write, and every Storage folder the app / dashboard uploads to (found from their upload call sites) has its own match. Emulator tests per phase (`firestore.rules`, `.phase8`, `.phase9`, `.phase10`, `.phase11`, `storage.rules`) cover the four operations for signed-out visitors, signed-in strangers, owners, sellers and admins, and query safety (lists must carry the filter the rules check).

**Security notes (Phase 10).** Identity is what Firebase Auth verified, never what a profile says: gift-card recipients are matched on the Auth phone number / verified email, and the rules only accept a profile `phone` equal to the ID token's `phone_number`. Every privileged path checks the live document behind the claim — admins (`admins/{uid}` role) in the rules and the callables, sellers (store `active`, `ownerUid`) — so a revocation takes effect at once. Callables validate every input (types, lengths, ids without `/`, amounts as whole IQD within bounds, photo URLs = the caller's own Storage uploads) and answer curated messages (internals only in the logs; `internal` otherwise). Public or abusable callables are rate-limited: `sendOtp` (per phone / IP / platform per day), `verifyOtp` (5 attempts per code, 15 wrong codes per phone per day), `aiGiftSearch` (per user / IP / all guests per day), `redeemGiftCard` (10 wrong codes / hour), `joinSecretSanta` (10 wrong codes / hour), `submitPartnerApplication` (5 / day), `createPaymentSession` (20 / hour), `checkPaymentStatus` (6 / session / 5 min); App Check (enforced at launch) is the first line in front of all of them — the per-IP limits rely on the request IP the platform reports. Logs never hold OTP codes (outside the Functions emulator), tokens or full phone numbers (masked `+964 750 ••• 4567`). Money, stock and counters only change inside transactions; every trigger is idempotent. The two HTTPS endpoints (`health`, `zainCashReturn`) serve GET / HEAD only, escape everything they echo and never redirect elsewhere. Before launch: `ZAINCASH_ENV=prod` with the merchant credentials (in `test` sandbox payments mark real orders paid — logged as an error on a deployed project), `ENFORCE_APP_CHECK=true`, the production rules in `firebase.json`.
